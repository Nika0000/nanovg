How this works

This is the real NanoVG — src/nanovg.c plus the GLES3 backend from nanovg_gl.h — compiled to WebAssembly and drawing into a WebGL2 canvas. The nvg object mirrors the C API one call at a time, so anything you write here translates directly to C.

Sketch contract

Your code is the body of a function called once per frame, between nvgBeginFrame() and nvgEndFrame(). In scope:

  • nvg — the API surface (see the reference below)
  • t, dt — seconds since compile, and since last frame
  • frame — frame counter
  • w, h — canvas size in CSS pixels
  • mouse — {x, y, down, inside}
  • cache — persists across frames, reset on recompile

Fonts sans, bold, light and icons are preloaded; cache.img holds a sample image.

Editor

  • nvg. opens completion with the header's own doc comment and the C signature each call maps to.
  • Ctrl/Cmd + Space asks for it anywhere; Esc dismisses it.
  • Matching is fuzzy — rndrct finds roundedRect, and the C name finds the JS one.
  • Enter or Tab accepts. Inside a call, a strip above the caret shows the parameter list with the current one in bold.
  • Ctrl/Cmd + Enter runs; editing recompiles on its own after a short pause.

Differences from C

  • No ctx first argument — there is one context.
  • Colors are plain arrays; nvg.hex('#7aa2f7') is a shortcut.
  • Paints are opaque handles, used exactly like the C values.
  • Out-param functions return objects: nvg.textBounds(x, y, s) gives {advance, xmin, ymin, xmax, ymax, width, height}.
  • Enum names drop the NVG_ prefix (both spellings work).
  • The optional end substring pointer is omitted.

Reading the inspector

NanoVG records a frame's work into its own buffers and submits it all in one flush at nvgEndFrame(). Draw calls is how many passes that flush needed — one per fill, stroke or text, since nanovg does not merge shapes. The breakdown names what each one does: a convex path is a single pass, a concave one is stencil-then-cover, text is triangles from the glyph atlas. Vertices is the geometry the tessellator produced, which is where curve-heavy paths actually get expensive. The What a frame costs example makes both readable.
